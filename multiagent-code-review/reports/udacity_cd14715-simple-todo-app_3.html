📁 File Details

📄 src/premium.ts

Quality score 0/100 · Estimated coverage 0% · No tests found

This file has critical security vulnerabilities that must be addressed before production deployment. The most severe issue is handling raw credit card data (cardNumber, CVV) directly in application code, violating PCI-DSS compliance requirements - payment tokenization via a third-party processor is mandatory. Additionally, client-controlled payment amounts enable payment bypass attacks, floating-point money calculations cause rounding errors, and race conditions in payment processing risk double-charging or inconsistent state. The code would benefit from using a payment gateway SDK, database transactions, and integer-based currency handling.

Issues (14)

  • CRITICAL security · line 16: Sensitive payment card data (cardNumber, cvv) stored in plaintext in PaymentDetails interface. This violates PCI-DSS requirements and exposes critical financial information. The card data should never be handled directly by application code.
    Fix: Never handle raw card data. Use a PCI-compliant payment processor (Stripe, Square) that provides tokenization. Replace PaymentDetails with: { paymentToken: string; amount: number; }. The payment processor handles card validation and returns a token to use.
  • CRITICAL security · line 115: Full credit card number (payment.cardNumber) accessible in application code and passed to chargeCard function. Even though only last 4 digits are stored, having the full card number in memory is a PCI-DSS violation and creates attack surface.
    Fix: Implement payment tokenization. Replace chargeCard signature with async function chargeCard(paymentToken: string, amount: number) and integrate with a payment gateway SDK that handles card data: const result = await paymentGateway.charge({ token: paymentToken, amount });
  • CRITICAL security · line 29: Payment amount provided by client in PaymentDetails parameter. This allows clients to manipulate payment amounts by sending arbitrary values, enabling payment bypass (e.g., paying $0.01 for enterprise tier).
    Fix: Never trust payment amount from client. Remove amount from PaymentDetails interface and only use server-calculated amount: const amount = calculateSubscriptionPrice(tier); const paymentSuccessful = await chargeCard(payment, amount);
  • HIGH bug-risk · line 95: Floating point arithmetic used for money calculations (basePrice * TAX_RATE, basePrice * PROCESSING_FEE). This causes rounding errors in financial calculations, potentially leading to incorrect charges or accumulated discrepancies.
    Fix: Use integer arithmetic with cents. Example: function calculateSubscriptionPrice(tier: 'premium' | 'enterprise'): number { const PRICING = { premium: 999, enterprise: 4999 }; const basePrice = PRICING[tier]; const TAX_RATE = 8; const PROCESSING_FEE = 29; return basePrice + Math.round(basePrice * TAX_RATE / 1000) + Math.round(basePrice * PROCESSING_FEE / 1000); } // returns cents
  • HIGH security · line 61: Client-side card validation only checks format (length, regex) but performs no cryptographic validation. The Luhn algorithm check is missing, allowing obviously invalid card numbers. More critically, validation should be delegated to payment processor.
    Fix: Remove client-side card validation entirely and use payment processor tokenization. If you must validate for UX, add Luhn check: function luhnCheck(cardNumber: string): boolean { let sum = 0; let isEven = false; for (let i = cardNumber.length - 1; i >= 0; i--) { let digit = parseInt(cardNumber[i]); if (isEven) digit *= 2; if (digit > 9) digit -= 9; sum += digit; isEven = !isEven; } return sum % 10 === 0; }
  • HIGH bug-risk · line 82: Expiry date validation has off-by-one error. new Date(2000 + parseInt(year), parseInt(month) - 1) creates a date at the START of the expiry month, so cards expire too early. A card with 12/24 would be considered expired on 12/01/2024 instead of 12/31/2024.
    Fix: Set to end of expiry month: const [month, year] = expiryDate.split('/'); const expiryDateObj = new Date(2000 + parseInt(year), parseInt(month), 0); // day 0 = last day of previous month, so month param gives end of that month
  • HIGH security · line 45: Race condition in payment processing. Between chargeCard and upgradeUserSubscription, multiple concurrent requests could charge the user multiple times but only upgrade once, or upgrade could fail after charge succeeds without refund.
    Fix: Wrap the payment and upgrade in a database transaction with idempotency key: const idempotencyKey = `${userId}-${tier}-${Date.now()}`; await db.transaction(async (trx) => { const existing = await trx.query('SELECT id FROM payments WHERE idempotency_key = $1', [idempotencyKey]); if (existing.length > 0) return true; const charged = await chargeCard(payment, amount, idempotencyKey, trx); if (!charged) throw new Error('Payment failed'); await upgradeUserSubscription(userId, tier, trx); });
  • HIGH security · line 167: JSON.parse called on database field subscription.features without try-catch. If data is corrupted or modified externally, this throws unhandled exception and crashes the authorization check, potentially granting access by default or denying legitimate users.
    Fix: Add error handling with safe fallback: try { const features = JSON.parse(subscription.features); return features.includes(feature); } catch (error) { console.error('Invalid features JSON for user', userId, error); return false; // Fail closed for security }
  • MEDIUM security · line 124: Payment error logged to console.error with full error object. This may leak sensitive information like full card details, internal database structure, or connection strings to logs that could be accessed by unauthorized personnel.
    Fix: Log only safe, sanitized error details: console.error('Payment failed:', { userId, amount, errorMessage: error instanceof Error ? error.message : 'Unknown error' });
  • MEDIUM bug-risk · line 152: db.query result accessed as rows.length without checking if rows is an array. Different database libraries return results differently; if rows is undefined or the result shape changes, this throws TypeError.
    Fix: Use explicit type checking: const result = await db.query(query, [userId]); const rows = Array.isArray(result) ? result : result.rows || []; if (rows.length === 0) return false;
  • MEDIUM security · line 65: Card number validation only checks length === 16, but valid cards can be 13-19 digits (e.g., Amex is 15 digits, some Maestro are 19). This rejects legitimate payment methods.
    Fix: Accept valid card number lengths: if (cardNumber.length < 13 || cardNumber.length > 19 || !/^\d+$/.test(cardNumber)) { return false; }
  • MEDIUM bug-risk · line 188: JSON.parse(row.features) in getUserSubscription can throw if features field is corrupted, crashing subscription retrieval. Same issue as line 167.
    Fix: Add try-catch: try { return { userId: row.user_id, tier: row.tier, validUntil: new Date(row.valid_until), features: JSON.parse(row.features) }; } catch (error) { console.error('Invalid subscription data for user', userId); return null; }
  • LOW security · line 33: Generic error message 'Invalid payment details' thrown without specifying which field failed validation. While this prevents information leakage, it makes legitimate debugging difficult and provides poor UX.
    Fix: Return structured validation errors in development, generic in production: if (!validatePaymentDetails(payment)) { const errors = getDetailedValidationErrors(payment); if (process.env.NODE_ENV === 'production') { throw new Error('Invalid payment details'); } throw new Error(`Invalid payment: ${errors.join(', ')}`); }
  • LOW bug-risk · line 138: Subscription validUntil calculated using setFullYear which can produce unexpected results on leap years or edge dates. For example, if today is Feb 29, 2024, adding 1 year produces Feb 28, 2025, shorting users one day.
    Fix: Use explicit date arithmetic: const validUntil = new Date(Date.now() + 365 * 24 * 60 * 60 * 1000); // Or use a date library like date-fns: import { addYears } from 'date-fns'; const validUntil = addYears(new Date(), 1);
