📄 src/todo.ts

Quality score 0/100 · Estimated coverage 15% · Tests: src/todo.test.ts

This file contains three critical SQL injection vulnerabilities (lines 121, 132, 143) that allow attackers to execute arbitrary SQL commands. The new search functionality added in PR #2 introduces these serious security flaws through string concatenation instead of parameterized queries. Additionally, the ID generation uses insecure Math.random() instead of cryptographic methods. Positively, the existing CRUD functions (getTodoById, createTodo, updateTodoStatus, deleteTodo) correctly use parameterized queries, demonstrating the developer knows the secure pattern but failed to apply it to the new search features.

Issues (11)

  • CRITICAL security · line 121: SQL injection vulnerability via direct string interpolation of user input in LIKE clause. An attacker can inject malicious SQL by providing input like: `%' OR '1'='1` or `'; DROP TABLE todos; --` to extract data, modify records, or execute arbitrary SQL.
    Fix: Use parameterized queries: `const query = 'SELECT * FROM todos WHERE title LIKE $1 OR description LIKE $1'; const rows = await db.query(query, [`%${keyword}%`]);`
  • CRITICAL security · line 132: SQL injection vulnerability via direct string concatenation of unvalidated user input. An attacker can provide input like `1 OR 1=1` or `1; DROP TABLE todos; --` to bypass the WHERE clause or execute arbitrary SQL commands.
    Fix: Use parameterized query and validate boolean input: `const isCompleted = completed === 'true'; const sql = 'SELECT * FROM todos WHERE completed = $1'; const rows = await db.query(sql, [isCompleted]);`
  • CRITICAL security · line 143: SQL injection vulnerability via template literal with unsanitized userId. An attacker can inject SQL by providing input like: `' OR '1'='1` or `'; DELETE FROM user_todos; --` to access unauthorized data or manipulate the database.
    Fix: Use parameterized queries: `const query = 'SELECT t.* FROM todos t JOIN user_todos ut ON t.id = ut.todo_id WHERE ut.user_id = $1'; const rows = await db.query(query, [userId]);`
  • HIGH security · line 152: Using Math.random() for ID generation is cryptographically insecure and predictable. Date.now() provides only millisecond precision, creating collision risk under concurrent requests. This could lead to ID prediction or collisions.
    Fix: Use crypto.randomUUID() for secure unique IDs: `import { randomUUID } from 'crypto'; function generateId(): string { return randomUUID(); }` or use a database sequence/auto-increment.
  • MEDIUM security · line 40: HTML entity encoding is insufficient for all XSS contexts. This sanitization only works for HTML content contexts, not for attributes, JavaScript, or CSS contexts. Additionally, sanitizing at storage layer means data is permanently altered.
    Fix: Remove sanitization from storage layer and apply context-appropriate escaping at the presentation layer. Use a library like DOMPurify or template engines with auto-escaping. Store original data and escape on output.
  • MEDIUM bug-risk · line 102: updateTodoStatus does not verify that the todo exists before updating. If an invalid ID is provided, the operation silently succeeds with 0 rows affected, providing no feedback to the caller.
    Fix: Check affected rows and throw error if todo not found: `const result = await db.query(query, [completed, id]); if (result.rowCount === 0) { throw new Error('Todo not found'); }`
  • MEDIUM bug-risk · line 110: deleteTodo does not verify that the todo exists before deletion. Silent success on non-existent IDs can mask bugs and make it difficult to distinguish between successful deletion and no-op.
    Fix: Check affected rows and return status or throw: `const result = await db.query(query, [id]); if (result.rowCount === 0) { throw new Error('Todo not found'); } return result.rowCount > 0;`
  • MEDIUM bug-risk · line 130: searchTodosByStatus accepts a string parameter for a boolean field without type validation. This creates confusion about expected input ('true'/'false' strings vs '1'/'0' vs booleans) and enables SQL injection.
    Fix: Change parameter type to boolean: `export async function searchTodosByStatus(completed: boolean): Promise<Todo[]> { const query = 'SELECT * FROM todos WHERE completed = $1'; const rows = await db.query(query, [completed]); return rows as Todo[]; }`
  • LOW bug-risk · line 82: Type assertion 'as Todo[]' bypasses type safety. Database rows may not match the Todo interface (e.g., created_at vs createdAt naming, missing fields). This could lead to runtime errors when accessing Todo properties.
    Fix: Add runtime validation or mapping: `return rows.map(row => ({ id: row.id, title: row.title, description: row.description, completed: row.completed, createdAt: new Date(row.created_at) }));`
  • LOW security · line 119: No input validation on the keyword parameter. An empty string or excessively long string could cause performance issues or unexpected behavior. LIKE queries with user input should have length limits.
    Fix: Add input validation: `if (!keyword || keyword.trim().length === 0) { throw new Error('Search keyword is required'); } if (keyword.length > 100) { throw new Error('Search keyword too long'); }`
  • INFO best-practice · line 88: getTodoById correctly uses parameterized queries to prevent SQL injection. This is good security practice and should be the pattern for all database queries in this file.
    Fix: Continue using this pattern. Consider extracting common query logic into a database helper layer.
